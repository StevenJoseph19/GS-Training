1. React useEffect Infinite Loop (Stale Dependency)

const [count, setCount] = useState(0);

useEffect(() => {
  setCount(count + 1);
}, [count]);

Q: Why does this cause an infinite loop?
Fix this to run once on mount:-

useEffect(() => {
  setCount(c => c + 1);
}, []); // no dependencies, runs only once after first render

  console.log(count);

useCallback(() => console.log(count), [count]);

9.Conditional Rendering Quirk: Returning Zero
The Question Imagine you have a component that displays a notification count. 
The count is stored in the count state variable.
function NotificationBadge({ count }) {
  return (
    <div>
      <p>Notifications</p>
      {count && <span className="badge">{count}</span>}
    </div>
  );
}

Question:

If count is passed as 0 (meaning no notifications), what will the component render in the browser?

Answer:

React will render the number 0 directly into the DOM instead of rendering the <span> badge element.

The component output will be: <div><p>Notifications</p>0</div>

The Explanation
In JavaScript, the expression 0 && <span className="badge">0</span> evaluates to the first falsy operand, which is 0.

React handles null, undefined, and false correctly by rendering nothing.

However, React treats the number 0 as a special case: it is a JavaScript falsy value, but React renders it as the string "0" in the DOM.

The Fix
To explicitly prevent rendering the number 0 when you intend to render nothing, you must ensure the expression evaluates to false, null, or undefined.

Fix 1: Explicit Comparison (Recommended)

Check for a truthy value (i.e., greater than zero).

// Check if count is greater than 0
{count > 0 && <span className="badge">{count}</span>}

Fix 2: Use the Logical NOT Operator

Convert the falsy value 0 into the boolean true (using !), then back into false (using !!). This works because !!0 is false.


// Forces the expression to evaluate to a boolean
{!!count && <span className="badge">{count}</span>}

15. Callback with Stale State 

function Counter() { 

  const [count, setCount] = useState(0); 

  const handleClick = useCallback(() => { 

    setCount(count + 1); 

  }, []); 

  return <button onClick={handleClick}>Count: {count}</button>; 

} 

Question: 

Will setCount(count + 1) work correctly on every click? 

Answer: 

 No, count is stale (always 0). 

1. The Initial Render (The Snapshot)
When the Counter component first runs (the initial mount):

The state is initialized: count is 0.

The handleClick function is created using useCallback([], ...):

useCallback sees the empty dependency array ([]) and decides it will never recreate this function instance.

Crucially, the JavaScript closure is created. The function captures the variable environment from that moment in time, freezing the value of count within its definition to 0.

Fix: Use functional update: setCount(c => c + 1); 
The "Why": 
Stale Closures
When you use useCallback with an empty dependency array [], React creates the function instance only once (during the initial mount).Because JavaScript functions "close over" (capture) the variables in their scope when they are defined, handleClick captures the variable count exactly as it existed during that first render: 0.No matter how many times the component re-renders with a new count (1, 2, 3...), the handleClick function instance remains the same "frozen" version from the first render, holding onto the old value of 0.
The Code Fixes
There are actually two ways to fix this, though the one you noted (Functional Update) is usually preferred for counters.
Option 1: Functional State Update (Preferred)
By passing a function to setCount, you bypass the closure issue. React passes the current state value into the arrow function at the exact moment the update happens.
const handleClick = useCallback(() => {
  // 'prevCount' is guaranteed to be the latest state
  setCount(prevCount => prevCount + 1); 
}, []); // Dependency array remains empty
Option 2: Correct Dependency ArrayIf you must use the count variable directly, you must tell useCallback to recreate the function whenever count changes.
const handleClick = useCallback(() => {
  setCount(count + 1);
}, [count]); // Function is recreated every time 'count' changes
Note: This effectively negates the performance benefit of useCallback if the parent re-renders frequently, as the function reference changes on every click.
Summary Table
Approach               Dependency Array     Behavior                                   Result
Current (Buggy)        []                   Captures count at mount (0).               Stuck at 1.
Functional Update      []                   Uses current state from React internals.   Correct (1, 2, 3...)
Dependency Fix         [count]              Recreates function when count changes.     Correct (1, 2, 3...)

18. Custom Hook State Reset
// A simple custom hook
const useCounter = (initialValue = 0) => {
  const [count, setCount] = useState(initialValue);
  return [count, setCount];
};

// ChildComponent implementation:
function ChildComponent({ initialValue }) {
  // uses the prop to initialize state
  const [count, setCount] = useCounter(initialValue); 
  // ... rest of component
}
Question: If the parent changes the initialValue prop from 5 to 20 after the child has already rendered, will count update to 20?

Answer:

No. useState only uses the initial value argument (initialValue) during the first render. Subsequent changes to the prop are ignored by useState.

Fix: Use a second useEffect hook inside ChildComponent to explicitly watch for changes and manually update state:

useEffect(() => {
  setCount(initialValue);
}, [initialValue]);

20. map() Without Keys Warning

function List({ items }) {
  return (
    <ul>
      {items.map((item) => (
        <li>{item.name}</li>
      ))}
    </ul>
  );
}

Question: What is the critical error in the code above?

Answer:

Critical Error: The list items are missing the required key prop.

Impact: React cannot reliably track element identity when the list changes (items added/removed/reordered), leading to performance issues and potential state mix-ups.

Fix: Use a stable, unique ID from the data:
{items.map((item) => (<li key={item.id}>{item.name}</li>))}

Answer:

No, it is likely hurting performance (or at best, neutral).

22. React Event Bubbling vs. event.stopPropagation()

// Two nested event handlers
<div onClick={() => console.log('Outer Click')}>
  <button onClick={() => console.log('Inner Click')}>Click Me</button>
</div>

Question: When the "Click Me" button is pressed, what is logged, and how can we make sure only 'Inner Click' is logged?

Answer:

Output: Both 'Inner Click' and 'Outer Click' are logged (due to event bubbling).

Fix: Use the event.stopPropagation() method inside the inner handler:
<button onClick={(e) => { e.stopPropagation(); console.log('Inner Click'); }}>

24. Missing Cleanup in useEffect with Object Dependency

function DataFetcher({ query }) {
  const [data, setData] = useState(null);

  useEffect(() => {
    let ignore = false;
    
    // Assume fetchById is an async function
    fetchById(query.id).then(result => {
      if (!ignore) {
        setData(result);
      }
    });

    // Cleanup function is missing!
    // return () => {}; 
  }, [query.id]); // Dependency array uses a nested property

  // ... rest of component
}

Question: What two potential problems does the missing cleanup function create when the query.id changes rapidly?

Answer:

Problem 1: Race Condition (Stale Update): If the ID changes rapidly, the first, slower fetch might complete after the second, faster fetch. The slower result overwrites the newer data, causing the UI to briefly show stale information.

Problem 2: Memory Leak (Minor): While React and modern browsers handle many memory leaks, the component might still hold references to variables (like setData) after it's unmounted, which is poor practice.

Fix: Implement the cleanup function to set the ignore flag to true. This tells the asynchronous then block to abandon the update if the effect has been cleaned up (i.e., if the ID changed or the component unmounted).

// Add the cleanup:
return () => {
  ignore = true; // Prevents calling setData on the outdated fetch
};
